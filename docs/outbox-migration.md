# Migrating to the official NestJS outbox

`@nestjs/outbox` owns the `nest_outbox` schema. Migration `0003_official_outbox` contains the versioned SQL generated by `PostgresOutboxStore.migrationSql({ statementBreakpoints: true })` from version `0.1.0`. Application startup uses `migrate: false`, so the deployment role applies DDL and the runtime role only checks the schema. Continue running `pnpm drizzle-kit migrate` before starting each release.

For a fresh database, apply all migrations and start the application.

For an existing installation:

1. Stop all instances of the legacy application. Its relay must stop before the migration imports pending messages.
2. Back up the database and inspect `public.outbox_messages`. Its `occurred_at` column has no timezone; migration 0003 interprets those values as UTC. Verify the legacy writers' database session timezone and timestamp conventions. If they stored local wall times, reconcile their interpretation in a reviewed migration before running this import. Rows with `processed_at IS NULL` are imported into `nest_outbox.messages`, preserving their event ID, topic, payload and UTC timestamp. The import ignores already-present IDs and leaves all legacy rows intact.
3. Apply migrations with `pnpm drizzle-kit migrate`.
4. Update event listeners to `@OnOutboxMessage(topic, { consumer: 'stable-consumer-name' })` before restarting the application. A topic without a consumer is retried and eventually dead-lettered. The boilerplate has no production consumers; applications add their own.
5. Reconcile legacy rows with `processed_at IS NOT NULL` against their actual effects. The previous relay wrote that timestamp before delivery, so it does not prove delivery succeeded. Never replay that entire history automatically. After checking downstream effects, explicitly requeue only events that need recovery and whose consumers can handle duplicates.
6. Restart the updated application. Monitor `OutboxRelay.stats()` and inspect failed messages through `OutboxDeadLetters`.

The legacy table remains declared in Drizzle so future schema generation does not silently drop this audit history. The application no longer reads or writes it. A later, reviewed migration can archive or remove it after reconciliation.

New aggregate writes call `publisher.publish(aggregate, transaction)` inside the transaction that saves the aggregate. The adapter preserves domain event IDs and uses the aggregate ID as the ordering key. The relay polls committed messages; the adapter deliberately does not call `notify()` inside an uncommitted transaction. An application can inject the official `Outbox` and call `notify()` after commit if it needs lower latency.

Consumer inbox identities are part of the delivery contract. Keep them stable across releases. For database effects, call `context.processInTransaction(transaction, work)` inside the same transaction as those effects. For external effects, use the remote service's idempotency key or another durable duplicate guard.

See the [official outbox documentation](https://docs.nestjs.com/reliability/outbox) for routing, retries, dead-letter requeueing and inbox retention.
